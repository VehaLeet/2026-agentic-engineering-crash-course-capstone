## Why

Головна обіцянка брифу — «сервіс сам відстежує появу нових даних і сповіщає в Telegram». Поки
що він лише збирає й показує дані: щоб дізнатися про нові результати РДН, треба відкрити UI або
термінал. Детекція змін (зріз 4) уже каже, які саме доби постачання змінилися, тож лишилося
донести цей факт до людей. Від цього зрізу залежить критерій MVP «сповіщення приходить рівно
один раз на кожне реальне оновлення».

## What Changes

- **Сповіщення після кожного запуску збору зі статусом `success`.** Одне повідомлення в Telegram
  кожному ввімкненому отримувачу. У ньому по кожній зміненій добі постачання: дата, мінімальна й
  максимальна ціна та середньозважена ціна (та сама, яку публікує ОРЕЕ). Якщо доба вже була в БД
  і змінилася, її позначено як перераховану.
- **Інші статуси не сповіщають:** `no_changes`, `no_data`, `skipped_locked` і `error` не
  надсилають нічого, як і бекфіл історії.
- **Таблиця отримувачів у БД** (`chat_id`, увімкнено/вимкнено). До появи UI налаштувань нею
  керують командою `python -m app.notify recipients add | list | remove`. Зріз 9 додасть API до
  тієї самої таблиці, без перенесення даних.
- **Журнал доставок у БД**: для кожної пари «запуск + отримувач» записуються стан (`pending`,
  `sent`, `failed`), кількість спроб і текст помилки. Унікальність пари гарантує, що один запуск
  ніколи не надішле одному отримувачу два повідомлення.
- **Надійність відправки**: таймаут, до 3 спроб на мережеві збої, 5xx і 429 (з урахуванням
  `retry_after` від Telegram). Без повторів на 400/403: «чат не знайдено» чи «бот заблоковано»
  повтор не виправить. Помилка одного отримувача не зриває відправку решті, а результат збору від
  доставки не залежить.
- **Прямий виклик Bot API** `sendMessage` через httpx, без бібліотек ботів (бриф).
- **Токен лише з env** (`TELEGRAM_BOT_TOKEN`) і ніколи в логах: URL Bot API містить токен, тож
  тексти помилок очищаються від нього. Без токена сповіщення вимкнені, і збір працює як раніше.
- **Команда перевірки** `python -m app.notify test`: надсилає тестове повідомлення всім
  отримувачам і показує результат по кожному. Так можна перевірити токен і `chat_id`, не чекаючи
  на нові дані ОРЕЕ.

### Що НЕ входить у цю зміну

- UI і API для отримувачів та глобальний вимикач сповіщень — зрізи 9 і 11b.
- Автоматичне повторне надсилання доставок, що лишилися `pending` після загибелі процесу.
- Інтерактивний бот: команди, відповіді, підписка з Telegram (non-goal брифу).
- Сповіщення про помилки збору, щоденні зведення, графіки в повідомленнях.
- Інші канали (email, Slack).
- Планувальник (зріз 8): поки що сповіщення надходять після ручного запуску з UI чи CLI.

## Capabilities

### New Capabilities

- `telegram-notify`: сповіщення в Telegram про реальні оновлення результатів РДН — вміст
  повідомлення, коли надсилати, а коли ні, керування отримувачами, журнал доставок із
  гарантією «не більше одного повідомлення на запуск для одного отримувача», надійність відправки
  і захист токена.

### Modified Capabilities

Немає. `collection-run` не змінює своїх вимог: статуси й журнал запусків лишаються тими самими.
Сповіщення — наслідок статусу `success`, описаний у новій здатності, а результат запуску від
доставки не залежить.

## Impact

- **Backend:** модуль `app/notify/` (клієнт Bot API, побудова повідомлення, відправка з журналом,
  CLI), виклик сповіщення наприкінці `collect_once` при `success`.
- **Схема БД:** міграція `0003` — таблиці `telegram_recipients` і `notification_deliveries`.
- **Env:** `TELEGRAM_BOT_TOKEN` (необов'язковий; без нього сповіщення вимкнені). Оновити
  `.env.example`.
- **Залежності:** нових немає (httpx уже є).
- **Зовнішня система:** `api.telegram.org`. Для живої перевірки потрібні справжній токен бота і
  `chat_id`.
- **Frontend:** без змін.
