## Context

Мотивація і межі зміни описані в `proposal.md`, вимоги — у `specs/http-api/spec.md`.

Що вже є:

- `collect_once(source, repository, runs, engine, reference_date, trigger)` бере блокування
  записувачів, створює рядок журналу, виконує збір і повертає `CollectOutcome`.
- `RunLog` має `start`, `finish`, `get(run_id)` і `state()` → `RunState(last_run, last_update,
  recent_errors)`.
- `RunInfo` уже містить усе, що потрібно віддати назовні: `id`, `started_at`, `finished_at`,
  `status`, `trigger`, `changed_days`, `error_message`.
- Опорна дата зараз береться як `date.today()`, тобто за годинником хоста.

Обмеження, які визначають дизайн:

- Збір зазвичай триває 1–3 с, а в найгіршому разі близько 90 с (3 спроби по 30 с таймауту).
  Тому ручний запуск асинхронний (див. proposal).
- Процес один і має один воркер: фонові задачі живуть у пам'яті процесу. Кілька воркерів
  бриф виключає прямо.
- Секрети беруться лише з env.

## Goals / Non-Goals

**Goals:**

- Відповідь на `POST /collect` не залежить від того, наскільки швидко відповідає ОРЕЕ.
- Жоден запуск, ініційований через HTTP, не губиться безслідно, навіть якщо процес загинув
  посередині.
- Помилка конфігурації автентифікації видна при старті, а не під час першого запиту.
- Тести проходять без мережі й без запущеного uvicorn.

**Non-Goals:**

- Черга фонових задач (Celery, RQ, arq). Одночасних записувачів щонайбільше один завдяки
  блокуванню, тож черга не дає жодного виграшу.
- Скасування запущеного збору через API.
- Ролі та кілька користувачів.

## Decisions

### Фонові запуски — власний менеджер задач, а не `BackgroundTasks` FastAPI

`BackgroundTasks` виконує задачу в тому самому ASGI-виклику, одразу після відправки відповіді.
Звідси дві проблеми. Застосунок не має способу дочекатися чи скасувати ці задачі при зупинці.
А в тестах через `httpx.ASGITransport` виклик повертається лише тоді, коли фонова задача вже
завершилась, тож перевірити сценарій «запуск ще триває» стає неможливо.

Натомість `RunManager` у `app.state`:

```
start(run_id) -> asyncio.create_task(collect_once(..., run_id=run_id))
                 посилання на задачу зберігається в set, щоб її не прибрав GC;
                 по завершенні задача сама видаляється з set
wait_all()    -> для тестів і для зупинки процесу
shutdown()    -> скасовує незавершені задачі й чекає на них
```

Незавершений через зупинку запуск лишає в журналі рядок з `finished_at IS NULL`. Так
задумано ще в `collection-run`: це видимий слід, а не втрата.

Альтернативу — окремий процес-воркер — відкинуто: для одного користувача й одного записувача
це зайва інфраструктура.

### Рядок журналу створюється в обробнику, до спроби взяти блокування

Щоб одразу повернути `run_id`, рядок мусить існувати вже в момент відповіді. Тому `POST
/collect` робить `runs.start("manual")` синхронно, а фонова задача викликає
`collect_once(..., run_id=run_id)`. Для зрізу 4 змінюється одне: якщо `run_id` передано,
`collect_once` не створює новий рядок, а використовує переданий. Тоді запуск, що не отримав
блокування, завершує той самий рядок статусом `skipped_locked`.

Наслідок цього порядку: рядок з'являється в журналі на кілька мілісекунд раніше, ніж
береться блокування. Вимоги `collection-run` від цього не змінюються. Кожен запуск так само
записується, пропущений запуск так само має `skipped_locked`, і збір так само не чекає на
блокування.

Альтернатива — брати блокування в обробнику і передавати його у фонову задачу. Відкинута:
advisory lock сесійний, тобто прив'язаний до конкретного з'єднання. Передавати з'єднання між
задачами крихко, а якщо фонова задача впаде до звільнення, з'єднання повернеться в пул із
заблокованим ключем.

### Опорна дата — Europe/Kyiv

`kyiv_today()` = `datetime.now(ZoneInfo("Europe/Kyiv")).date()` винесено в одну допоміжну
функцію, яку використовують API, `collect` і `backfill`. Функція приймає `now` як параметр,
тож у тестах час підставляється без підміни системного годинника. Залежність `tzdata`
гарантує, що часовий пояс знайдеться і в мінімальних образах без системної бази поясів.

Чому це важливо: правило двох кварталів із `dam-source` обчислює кварталі від опорної дати.
Якщо в контейнері з UTC 30.09 о 22:30 (у Києві це вже 01.10) взяти дату хоста, збір
завантажить Q3 і Q4. Це випадково збігається з правильним набором. А ось 31.12 о 22:30 UTC
збір завантажить Q4 і Q1 замість Q1, і це вже помилка, яку ніхто не помітить.

### Автентифікація — `HTTPBasic` + `secrets.compare_digest`, закрита за замовчуванням

Креди `API_USERNAME` / `API_PASSWORD` читаються один раз при створенні застосунку. Якщо
хоча б один не заданий, `create_app` кидає помилку конфігурації, і uvicorn не стартує.
Порівняння йде через `secrets.compare_digest` над байтами UTF-8, окремо для логіна й пароля,
і результати поєднуються без короткого замикання. Тоді час відповіді не видає, яка саме
частина кредів хибна.

Автентифікація підключається як залежність на рівні роутера, а не окремо на кожен маршрут.
Так новий маршрут зрізу 6 отримає її автоматично і не залишиться випадково відкритим.
`/health` живе поза цим роутером.

### Фабрика застосунку з підставними залежностями

`create_app(settings, engine=None, source=None)`: у продакшені engine і `OreeDamSource`
створюються в lifespan, а тести передають testcontainers-engine і `FakeDamSource`. Тести
входять у `app.router.lifespan_context(app)` напряму, тож окрема бібліотека для lifespan
не потрібна.

### Контракти API

Усі часові мітки віддаються в ISO 8601 в UTC (Pydantic серіалізує зсув як `Z`), дати — як `YYYY-MM-DD`.

```
GET /health                      без автентифікації
  200 {"status": "ok"}

POST /collect                    Basic Auth
  202 {"run_id": 5, "status_url": "/runs/5"}
      Location: /runs/5
  401                            без кредів / хибні креди; запуск не створюється

GET /runs/{run_id}               Basic Auth; run_id — ціле
  200 Run
  404 {"detail": "run not found"}
  422                            run_id не ціле

GET /status                      Basic Auth
  200 {"last_run": Run | null,
       "last_update": Run | null,      -- останній success
       "recent_errors": [Run, ...]}    -- до 5, найновіші першими

Run:
  {"id": 5,
   "started_at": "2026-09-28T10:00:00.123000Z",
   "finished_at": "2026-09-28T10:00:02.456000Z" | null,
   "status": "success" | "no_changes" | "no_data" | "error" | "skipped_locked" | null,
   "trigger": "manual" | "scheduled",
   "changed_days": ["2026-09-29"],
   "error_message": null | "FetchError: ..."}
```

Схема БД не змінюється.

### Запуск

```
$ uv run uvicorn app.api.main:app --workers 1
```

`app.api.main:app` будує застосунок з налаштувань env. `--workers 1` потрібен явно, бо фонові
запуски й менеджер задач живуть у пам'яті одного процесу.

## Risks / Trade-offs

- **Хтось запустить кілька воркерів** → дані не постраждають: стан запусків живе в БД, а
  взаємне виключення тримає advisory lock. Але `shutdown()` кожного воркера бачить лише власні
  задачі, а зріз 8 із планувальником у процесі запускав би розклад у кожному воркері. Тому
  обмеження «один воркер» зафіксовано в команді запуску і в брифі.
- **Процес загинув посередині фонового збору** → рядок лишається з `finished_at IS NULL`,
  блокування звільняється з обривом з'єднання. UI мусить уміти показати незавершений запуск
  (відкрите питання зрізу 4, переходить у зріз 11).
- **Необмежена кількість одночасних `POST /collect`** → кожен створює рядок журналу, але лише
  один отримує блокування, решта одразу завершуються `skipped_locked`. Для 1–5 внутрішніх
  користувачів за автентифікацією це прийнятно. Rate limiting — не в MVP.
- **Basic Auth передає креди з кожним запитом** → без TLS вони перехоплюються. Сервіс
  внутрішній; TLS термінується на рівні розгортання, яке поза цим зрізом. Записано в
  `docs/roadmap.md` разом із контейнеризацією.
- **`collect_once` отримує необов'язковий `run_id`** → з'являються дві гілки створення рядка.
  Пом'якшення: CLI і HTTP проходять той самий код збору, а тести зрізу 4 покривають гілку без
  `run_id`.

## Migration Plan

Міграцій БД немає. Розгортання: додати `API_USERNAME` і `API_PASSWORD` у `.env`, запустити
`uvicorn` з одним воркером. Відкат: зупинити процес. Дані й CLI-команди від нього не залежать.

## Open Questions

- Час життя незавершених запусків (`finished_at IS NULL`) після загибелі процесу. Їх можна
  прибирати при старті або показувати як є. Рішення стосується UI і не впливає ні на
  контракт, ні на задачі цього зрізу.
