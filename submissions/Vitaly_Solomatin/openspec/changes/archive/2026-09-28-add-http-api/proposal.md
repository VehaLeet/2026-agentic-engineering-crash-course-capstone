## Why

Після зрізу 4 збір існує лише як команда командного рядка: щоб запустити його чи дізнатися,
коли система востаннє перевіряла ОРЕЕ, треба мати shell на сервері. Кнопці «Оновити зараз» і
панелі статусу з брифу нема до чого звертатися. Цей зріз дає перший мережевий інтерфейс — рівно
той мінімум, що перетворює `collect_once` і журнал запусків на сервіс: запустити збір ззовні,
простежити його результат і прочитати стан, усе за автентифікацією.

## What Changes

- Застосунок FastAPI — перший довгоживучий процес проєкту.
- **HTTP Basic Auth** на всіх ендпойнтах, крім перевірки живості. Логін і пароль — лише з env
  (`API_USERNAME`, `API_PASSWORD`). Без них застосунок **не стартує**: відкритий API без пароля
  гірший, ніж API, що не запустився.
- `POST /collect` — **асинхронний**: створює рядок журналу, запускає збір у фоні і одразу
  відповідає `202` з `run_id` та посиланням на запуск. Відповідь не чекає на ОРЕЕ, тож не висить
  до ~90 с у найгіршому випадку ретраїв.
- `GET /runs/{run_id}` — стан одного запуску: поки триває — `status: null`; далі один із п'яти
  статусів, змінені доби, текст помилки. Це те, що опитуватиме UI після натискання кнопки.
- `GET /status` — стан системи з `collection-run`: останній запуск, останнє оновлення даних,
  останні помилки.
- `GET /health` — без автентифікації і без даних, для перевірки живості процесу.
- **Опорна дата — сьогодні за Europe/Kyiv**, а не за годинником сервера. Інакше в контейнері з UTC
  між 00:00 і 03:00 за Києвом збір брав би вчорашню дату і тягнув би не той квартал на межі
  кварталу. Та сама правка — у командах `collect` і `backfill`.
- Ручний запуск через HTTP позначається в журналі як `manual`.

### Що НЕ входить у цю зміну

- `GET /prices` і будь-яке читання цін — зріз 6 (`add-prices-read-api`).
- APScheduler і плановий запуск — зріз 8. Процес уже вміє тримати фонові задачі, але розкладу
  тут немає.
- Налаштування (отримувачі, інтервал, вимикач) — зріз 9.
- Telegram — зріз 7.
- Фронтенд, CORS для нього, сесії чи логін-форма: лише Basic Auth.
- **Dockerfile і сервіс `backend` у `docker-compose.yml`.** Застосунок запускається командою
  `uvicorn` локально. Контейнеризація — окремий невеликий зріз, щоб не роздувати ревʼю цього
  (записано боргом у `docs/roadmap.md`).
- Скасування запущеного збору, черга запусків, історія всіх запусків зі сторінками.
- Кілька воркерів: процес має працювати з **одним** воркером (фонові задачі живуть у процесі).

## Capabilities

### New Capabilities

- `http-api`: мережевий інтерфейс сервісу — автентифікація Basic Auth з кредами з env,
  асинхронний ручний запуск збору з опитуванням результату за ідентифікатором запуску, читання
  стану системи і перевірка живості.

### Modified Capabilities

Немає. `collection-run` використовується як є: API — ще один викликач того самого сценарію збору
і того самого журналу, а його вимоги (п'ять станів, неблокувальне взаємне виключення, запис
кожного запуску) лишаються незмінними. Те, що рядок журналу для HTTP-запуску створюється до
спроби взяти блокування, вимоги «кожен запуск записується» не змінює — це деталь реалізації
(див. `design.md`).

## Impact

- **Новий код:** `backend/app/api/` — застосунок, автентифікація, маршрути, менеджер фонових
  запусків.
- **Зміна наявного коду:** `collect_once` приймає вже створений `run_id`; `collect` і `backfill`
  беруть сьогоднішню дату за Europe/Kyiv.
- **Залежності:** `fastapi`, `uvicorn[standard]`, `tzdata` (щоб `Europe/Kyiv` був доступний і
  в мінімальних образах).
- **Env:** нові `API_USERNAME`, `API_PASSWORD`; `.env.example` оновлюється.
- **Схема БД:** без змін.
- **Операційне обмеження:** один воркер uvicorn.
- **Розблоковує:** зріз 6 додасть маршрут до вже автентифікованого застосунку; зріз 11 (UI)
  отримує контракт «Оновити зараз» → `202` → опитування `GET /runs/{id}`.
