## Context

Мотивацію й межі описано в `proposal.md`. Вимоги — дельти `specs/http-api`, `specs/prices-api`
і `specs/web-app`.

Поточний стан автентифікації в коді:

- `backend/app/api/settings.py`: `ApiSettings.from_env()` читає `API_USERNAME` / `API_PASSWORD`
  і кидає `ConfigError`, якщо їх немає. `create_app(settings=None)` викликає його, тож без
  кредів застосунок не будується.
- `backend/app/api/app.py`: `_require_auth`, залежність роутера `api` з `HTTPBasic` і
  `compare_digest`, повертає 401 з `WWW-Authenticate`. Роутер виставлено як
  `app.state.protected_router`, щоб тест перевіряв, що всі маршрути, крім `/health`, захищені.
- Тести: `tests/test_api.py` (конфігурація, 401, хибні креди, обхід маршрутів),
  `tests/test_prices.py` (`test_requires_auth`), хелпер `running()` і константа `AUTH`, яку
  використовують майже всі API-тести.
- Frontend: `ApiUnauthorized`, стан `unauthorized` у `useConnection`, посилання «Увійти» в
  `ConnectionPanel`, відповідні тести.
- Запуск: `uv run uvicorn app.api.main:app --workers 1`; uvicorn типово слухає `127.0.0.1`.
- `docker-compose.yml`: Postgres на `"5432:5432"`, тобто на всіх інтерфейсах.

## Goals / Non-Goals

**Goals:**

- Жодного коду автентифікації в backend і frontend, без залишків «на потім».
- Відкрити API в мережу можна лише свідомо, редагуючи код. Налаштування оточення для цього
  недостатньо.
- Поведінка решти API не змінюється: контракти, коди помилок валідації, фонові запуски.

**Non-Goals:**

- Захист від процесів на тій самій машині. Будь-який локальний процес може звертатися до API,
  і це прийнятно для однокористувацького MVP.
- Нова автентифікація в будь-якій формі.

## Decisions

### Localhost-only забезпечує власний запускач, а не документація

```
python -m app.api
   |
   +-- API_HOST (типово 127.0.0.1) --> is_loopback? --ні--> ConfigError, exit 1
   |                                        | так
   +-- API_PORT (типово 8000)               v
                               uvicorn.run("app.api.main:app", host, port, workers=1)
```

`app/api/__main__.py`:

- `resolve_host(value)` приймає `localhost` і будь-яку IP-адресу, для якої
  `ipaddress.ip_address(value).is_loopback`, тобто `127.0.0.0/8` і `::1`. Решту відхиляє з
  `ConfigError`, у повідомленні якого є сама адреса. Імена хостів, крім `localhost`, не
  розв'язуються через DNS, а відхиляються одразу: DNS може змінитися, а перевірка має бути
  детермінованою.
- `workers=1` зафіксовано в запускачі. Раніше ця вимога жила лише в команді запуску, і її
  легко було загубити.

Чому не перевіряти адресу всередині застосунку. `create_app` не знає, на якому інтерфейсі
слухає uvicorn: адреса належить серверу, а не ASGI-застосунку. Перевірка в запускачі — єдине
місце, де адреса відома до того, як відкрито сокет.

Обмеження, записане чесно: `uv run uvicorn app.api.main:app --host 0.0.0.0` запускачем не
перевіряється. Документація (`README`, бриф) вказує лише `python -m app.api`. Команду uvicorn
напряму ніде не згадано, тож «випадково» відкрити API в мережу не вийде, хіба свідомо.

Альтернативу — middleware, що відхиляє запити з не-loopback `client.host` — відкинуто. Порт
тоді однаково відкритий у мережу, а IP клієнта за будь-яким проксі стає loopback, тож захист
був би ілюзорним.

### Видаляємо, а не вимикаємо прапорцем

`API_AUTH_ENABLED=false` зберіг би код і тести автентифікації «на потім». Відкинуто: майбутня
автентифікація буде іншою (сесії, моделі `user`/`session`), тож нинішній Basic Auth не стане
її основою. Прапорець лише подвоїв би кількість станів, які треба тестувати. Історія в git
зберігає реалізацію, якщо вона колись знадобиться для порівняння.

### Тест «кожен маршрут, крім `/health`, захищений» перетворюється на протилежний

Раніше тест обходив маршрути `protected_router` і перевіряв 401. Тепер `protected_router`
зникає, а один тест обходить усі маршрути застосунку й перевіряє, що жоден не відповідає 401
без кредів. Так захищаємося від того, що автентифікація «повернеться» частково. Перевірку, що
`/docs`, `/redoc` і `/openapi.json` вимкнено, залишаємо: вона не стосується автентифікації.

### Хелпер тестів

`running(engine, source)` лишається. Константа `AUTH` і параметр `auth=AUTH` зникають з усіх
викликів механічно. Тести на відхилення кредів видаляються. Тести, де креди були лише
передумовою, лишаються без неї.

### Frontend

- `ApiUnauthorized` видаляється. 401, якщо колись прийде, стане просто неочікуваною відповіддю:
  `ApiContractError` → стан `error`, тобто видимою помилкою, а не тихим входом.
- Стан `unauthorized` зникає з типу `Connection`. TypeScript через вичерпний `switch` у
  `ConnectionPanel` сам покаже всі місця, де його треба прибрати.
- `credentials` лишається типовим. Заголовок `Authorization` не додається, і тест це стверджує.

### Postgres лише на `127.0.0.1`

`ports: ["127.0.0.1:5432:5432"]`. Застосунок і тести (`testcontainers`) підключаються через
`localhost`, тож для них нічого не змінюється. Зовні база з паролем `dam`/`dam` більше не
видна.

### Документація

- `docs/brief.md`: «Доступ до UI» і «TLS» → «MVP без автентифікації; доступ лише з localhost
  (API і база). Session-based auth з моделями `user`/`session` і TLS — окремий етап, до того
  як сервіс стане доступним будь-кому, крім розробника».
- `docs/roadmap.md`: зафіксувати поворот напряму. Борг «контейнеризація + TLS» переформулювати:
  TLS тепер іде разом із майбутньою автентифікацією. Зріз `add-web-login` не додавати.
- `frontend/README.md`: прибрати розділ «Вхід»; запуск backend — через `python -m app.api`.
- Розділи `Purpose` у `openspec/specs/http-api` і `openspec/specs/web-app` згадують
  автентифікацію, а дельта їх не змінює. Їх правимо в головних специфікаціях напряму, за
  правилами OpenSpec.

Схема БД і контракти відповідей не змінюються, змінюється лише те, що коду 401 більше немає.

## Risks / Trade-offs

- **Будь-який процес на цій машині має повний доступ до API** → прийнятно для MVP на машині
  розробника. Записується в бриф як обмеження етапу.
- **Прямий запуск `uvicorn --host 0.0.0.0` обходить перевірку** → його немає в документації,
  а обійти перевірку можна лише свідомо. Повна гарантія потребувала б мережевих правил ОС,
  тобто розгортання, що поза межами MVP.
- **Втрачаються тести автентифікації** → вони лишаються в історії git. Майбутня
  session-based автентифікація матиме власні, інші за змістом.
- **Хтось уже має `API_USERNAME`/`API_PASSWORD` у `.env`** → значення просто ігноруються, помилки
  немає.
- **`add-web-login` лишається в `openspec/changes/`** → після рішення користувача її варто
  видалити, інакше її дельти (зокрема MODIFIED «Автентифікація Basic Auth») конфліктуватимуть із
  цією зміною при архівуванні.

## Migration Plan

Міграцій БД немає. Розгортання: `docker compose up -d postgres`. Прив'язка порту змінюється
при перестворенні контейнера, дані в томі зберігаються. Далі `uv run python -m app.api`.
Відкат: повернути код попереднього коміту і `API_*` в `.env`.
