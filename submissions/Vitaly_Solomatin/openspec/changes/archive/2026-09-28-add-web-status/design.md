## Context

Мотивацію й межі описано в `proposal.md`, вимоги — у `specs/web-status/spec.md`.

Що вже є:

- **API (`http-api`).**
  - `POST /collect` → `202 {"run_id", "status_url"}`.
  - `GET /runs/{id}` → `Run` зі `status: null`, поки запуск триває.
  - `GET /status` → `{last_run, last_update, recent_errors}`, де помилок щонайбільше 5, найновіші
    першими.
  - Запуск, що наткнувся на блокування, завершується `skipped_locked` одразу.
  - Найгірший випадок збору — близько 90 с (3 спроби по 30 с таймауту).
- **Frontend.**
  - `api/client.ts`: `request(path)` робить лише GET, помилки розрізнено (`ApiUnavailable`,
    `ApiValidationError`, `ApiContractError`); типи `Run` і `SystemStatus` описано в `api/types.ts`.
  - `state/connection.ts`: `check()` зводить `/status` до `{ok, lastCheck, lastUpdate}`. Статус
    останнього запуску й помилки при цьому відкидаються.
  - `state/prices.ts`: `usePrices.load()` перечитує поточний діапазон.
  - `ConnectionPanel` рендериться в картці на початку `main`; `formatKyiv(iso)`; тема з
    `role="alert"` для помилок.

## Goals / Non-Goals

**Goals:**

- Один клік — від запуску до оновлених даних на екрані, без перезавантаження сторінки.
- Користувач ніколи не бачить «не завершено» або «помилка» для запуску, який штатно триває.
- Жодного вічного опитування: межа 2 хвилини, після неї кнопка знову доступна.
- Опитування тестується з фейковим часом, без реальних очікувань.

**Non-Goals:**

- Фонове оновлення стану без дії користувача.
- Скасування запуску.

## Decisions

### Клієнт: POST і типи

`request(path, init?)` отримує необов'язковий `RequestInit`. Сама обробка помилок не змінюється:
202 теж `ok`, тож тіло читається так само, як для 200.

```ts
startCollect(): Promise<{ run_id: number; status_url: string }>   // POST /collect
getRun(id: number): Promise<Run>                                   // GET /runs/{id}
```

Форма відповіді перевіряється мінімально: для `startCollect` — ціле `run_id`, для `getRun` —
наявність `id` і ключа `status`. Інакше кидається `ApiContractError`, як уже заведено в клієнті.

### Сховище ручного запуску

```ts
type Collect =
  | { phase: 'idle' }
  | { phase: 'running'; runId?: number }
  | { phase: 'done'; run: Run }                 // фінальний статус
  | { phase: 'timeout'; runId: number }         // > 2 хв без фінального статусу
  | { phase: 'failed'; message: string }        // запит на запуск чи опитування зірвався

useCollect: { collect: Collect; start(): Promise<void> }
```

`start()`:

1. Якщо `phase === 'running'`, нічого не робить. Це захищає від подвійного кліку незалежно від
   того, чи встигла кнопка стати недоступною.
2. `startCollect()` → `running(runId)`.
3. Цикл: `sleep(1000)` → `getRun(runId)`; вихід, коли `status !== null` або минув дедлайн 120 с.
4. `done` / `timeout` / `failed` залежно від результату.
5. Після фінального статусу: `useConnection.check()`; після `success` ще й `usePrices.load()`.

Інтервал 1 с. Типовий збір триває 1–3 с, тож результат з'являється за 1–3 опитування. Частіше
опитувати немає сенсу: це локальний API, а стан у БД змінюється лише раз наприкінці збору.

`sleep` і `now` передаються як залежності (за замовчуванням `setTimeout` і `Date.now`). Тести
керують ними фейковим часом Vitest і перевіряють межу 2 хвилини без реального очікування.

Альтернатива — `setInterval`. Відкинуто: наступне опитування мало б стартувати лише після
завершення попереднього, а з `setInterval` запити нашаровуються, якщо API відповідає повільніше
за інтервал.

### Стан системи: більше, ніж два часи

`Connection` у стані `ok` розширюється: до `lastCheck` і `lastUpdate` додаються
`lastRunStatus: RunStatus | null` і `recentErrors: Run[]`. Поля лише додаються, і наявні
тести й вимога `web-app` «Стан з'єднання з API» від цього не змінюються.

### «Не завершено» чи «виконується»

Поки наш запуск триває, `/status` повертає його як `last_run` зі `status: null`. Правило для
панелі:

```
collect.phase === 'running'          -> «Збір виконується…»      (незалежно від last_run)
last_run.status === null  (інакше)   -> «Останній запуск не завершено»
```

Друге можливе лише тоді, коли запуск перервався, наприклад процес загинув. Цей стан приходить
з `collection-run` (рядок з `finished_at IS NULL`) і був відкритим питанням зрізу 4 для UI.
Тепер його закрито.

### Повідомлення результату

| Статус | Текст | `role` |
|---|---|---|
| `success` | «Дані оновлено: 29.09.2026» (перелік змінених діб, DD.MM.YYYY) | `status` |
| `no_changes` | «Нових даних немає» | `status` |
| `no_data` | «ОРЕЕ ще не опублікував дані» | `status` |
| `skipped_locked` | «Збір уже виконується, спробуйте за хвилину» | `status` |
| `error` | «Помилка збору: <error_message>» | `alert` |
| timeout | «Збір триває довше, ніж очікувалось» | `status` |
| failed | «Backend недоступний» / текст помилки | `alert` |

`role="status"` — ввічливе оголошення для зчитувачів екрана, а не тривога. Так вимога «решта
статусів не показується як помилка» стає перевірною тестом, а не лише візуальною.

### Компоненти

```
components/CollectButton.tsx    кнопка + повідомлення результату (useCollect)
components/RecentErrors.tsx     перелік помилок або «Помилок збору немає»
components/StatusPanel.tsx      ConnectionPanel + «не завершено» + CollectButton + RecentErrors
App.tsx                         StatusPanel замість голої ConnectionPanel
```

`ConnectionPanel` лишається без змін і показує стан з'єднання. `StatusPanel` компонує все разом,
щоб логіка «виконується / не завершено» жила в одному місці.

Backend, API і схема БД не змінюються.

## Risks / Trade-offs

- **Кілька вкладок із відкритим UI** → кожна опитує лише свій запуск. Друга вкладка, запущена
  під час першої, отримає `skipped_locked` і так і скаже. Це правильна поведінка.
- **Після timeout збір насправді може ще завершитися** → кнопку знову розблоковано. Повторний
  клік або дасть `skipped_locked`, якщо той збір ще триває, або новий результат. Стан системи
  оновиться при наступній перевірці.
- **Повідомлення результату лишається до наступного кліку** → навмисно: користувач має
  встигнути прочитати. Автоприховування — не в MVP.
- **`recent_errors` обмежено 5 на backend** → повний журнал поза межами зміни.
