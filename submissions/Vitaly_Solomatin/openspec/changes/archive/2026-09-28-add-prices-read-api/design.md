## Context

Мотивація й межі зміни описані в `proposal.md`, вимоги — у `specs/prices-api/spec.md`.

Що вже є:

- `DamRepository.get_records(date_from, date_to)` повертає список `DamRecord` із включними
  межами, упорядкований за датою й періодом. Для перевернутого діапазону кидає `ValueError`.
- Застосунок `http-api` з автентифікацією на рівні роутера `api`. Новий маршрут, доданий до
  цього роутера, автоматично опиняється під Basic Auth, а тест «кожен маршрут, крім `/health`,
  захищений» тепер знатиме про `/prices`.
- `dam_prices` з первинним ключем `(delivery_date, period)`.

Заміри на dev-БД з усією історією (63 552 рядки):

| Запит | БД | Відповідь |
|---|---|---|
| погодинно, місяць | 4 мс | 0.04 МБ колонками |
| погодинно, рік | 37 мс | 0.51 МБ колонками / 1.60 МБ рядками |
| погодинно, уся історія | 315 мс | 3.66 МБ колонками / 11.59 МБ рядками |
| подобово, уся історія, `GROUP BY` у SQL | 25 мс | 2 648 рядків |

## Goals / Non-Goals

**Goals:**

- Будь-який діапазон вкладається в «< 1 с» разом із відображенням. Цього досягаємо тим, що
  погодинні дані обмежено за довжиною діапазону, а довгі діапазони агрегуються подобово.
- Та сама пара параметрів завжди повертає відповідь однієї форми.
- Подобові середні збігаються з тим, що публікує ОРЕЕ.

**Non-Goals:**

- Перетворення «дата + період» на мітку часу: за конвенцією проєкту це робить UI.
- Кешування і gzip: при таких замірах це передчасно.
- Нові індекси: первинний ключ уже покриває запити за діапазоном дат, а повне сканування
  всієї таблиці займає 5 мс.

## Decisions

### Явна роздільність, а не автоматичний поріг

Рішення ухвалив користувач (див. proposal). Якщо сервер сам вибирає роздільність за довжиною
діапазону, форма відповіді залежить від вхідних даних. Тоді таблиця «несподівано» втрачає
погодинні дані, коли діапазон переходить поріг. Явний `resolution` робить контракт
передбачуваним. За замовчуванням стоїть `hour`, бо це природний вигляд для таблиці за
короткий період.

### Ліміт погодинного діапазону — 366 діб

366 діб — це рівно один рік, враховуючи високосний, і не більше ніж 9 150 точок (366 × 25).
Такий обсяг — 0.5 МБ колонками, і його читання з БД займає 37 мс. Весь рік видно погодинно,
а довші діапазони свідомо переходять на `day`. Довжина рахується включно:
`(date_to − date_from).days + 1`. Помилка 422 прямо називає вихід: `resolution=day`.

### Агрегація в SQL

```sql
SELECT delivery_date,
       min(price), max(price),
       round(avg(price), 2)                                          AS price_avg,
       round(sum(price * volume_sell) / nullif(sum(volume_sell), 0), 2) AS price_weighted,
       sum(volume_sell), sum(volume_buy),
       sum(declared_volume_sell), sum(declared_volume_buy),
       count(*)                                                      AS periods
FROM dam_prices
WHERE delivery_date BETWEEN :date_from AND :date_to
GROUP BY delivery_date
ORDER BY delivery_date
```

Альтернатива — прочитати погодинні записи й агрегувати в Python. Відкинута, бо для всієї
історії довелося б тягнути 63 тис. рядків замість 2 648: 315 мс проти 25 мс.

`nullif(..., 0)` обробляє нульовий сумарний обсяг, і тоді `price_weighted` стає `null`, а не
помилкою ділення. Реальних діб із нульовим обсягом в історії немає, але сценарій це вимагає, і
тест перевіряє його на синтетичних даних.

### Дві середні з однозначними назвами

Звірка з ОРЕЕ за 26.09.2026 дала таке:

```
проста середня за періодами            6301.37   -> price_avg      (індекс BASE)
зважена за обсягом продажу             6560.60   -> price_weighted (= «середньозважена ціна» ОРЕЕ)
зважена за обсягом купівлі             6560.60   (на РДН обсяги продажу й купівлі рівні)
```

Обидві середні корисні: BASE — ринковий індекс, зважена — те, що ОРЕЕ показує як денну ціну.
Одне поле `price_avg` без уточнення було б пасткою для зрізу 7 з Telegram, де потрібна
«середня ціна». Зважувати беремо за обсягом продажу, бо на РДН продаж і купівля врівноважені,
а обсяг продажу — первинна колонка джерела.

### Колонковий формат

`{"field": [..], ...}` замість `[{"field": ..}, ...]`. За замірами це втричі менше, і масиви
підставляються в `series.data` ECharts напряму. Спільна вимога — усі масиви однакової довжини,
і i-й елемент кожного масиву описує одну точку.

### Числа — JSON-числа

`Decimal` конвертується у `float` лише на межі серіалізації. Ціни мають 2 знаки, обсяги — 1,
а агрегати вже округлені в SQL, тож похибка `float` на цьому масштабі не видна при
відображенні. Точну арифметику, як і раніше, виконують БД і Python-шар (`Decimal`). Рядки
замість чисел змушували б UI парсити кожне значення.

### Репозиторій

```
get_records(date_from, date_to)      наявний, без змін — для resolution=hour
get_daily(date_from, date_to)        новий -> list[DailyPrices]
    DailyPrices: delivery_date, price_min, price_max, price_avg, price_weighted | None,
                 volume_sell, volume_buy, declared_volume_sell, declared_volume_buy, periods
    (не DamDay — це ім'я вже зайняте моделлю таблиці хешів діб dam_days)
```

Валідацію параметрів (перевернутий діапазон, ліміт 366 діб, невідома роздільність) робить
шар API. Помилка повертається 422 ще до звернення до БД.

### Контракт API


## Risks / Trade-offs

- **`float` у JSON** → для відображення цього достатньо. Якщо колись знадобиться точний
  експорт, це буде окремий формат, бо експорт — non-goal MVP.
- **Ліміт 366 діб довільний** → він прив'язаний до виміряного обсягу і до «року». Змінити його
  можна однією константою, не змінюючи форму відповіді.
- **Таблиця погодинних даних за рік — це 8.8 тис. рядків** → це проблема відображення (зріз 10:
  віртуалізація чи сторінки в UI), а не API.
- **Дві середні можуть заплутати** → назви полів однозначні, і в контракті явно вказано, котра
  відповідає ОРЕЕ.
- **Поточна доба ще неповна?** → ні: ОРЕЕ публікує добу цілком одним аукціоном, тож часткових
  діб у джерелі немає, а агрегати не бачать «половини доби».
