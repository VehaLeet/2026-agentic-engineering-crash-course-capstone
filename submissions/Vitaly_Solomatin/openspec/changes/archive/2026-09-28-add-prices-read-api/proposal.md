## Why

У БД лежить уся історія РДН з 01.07.2019, 63 552 погодинні записи, але прочитати їх через API
поки неможливо. Графіку й таблиці з брифу немає звідки брати дані. Цей зріз додає читання цін
за довільний діапазон дат, і саме тут вирішується критерій MVP «історію за будь-який діапазон
видно на графіку за < 1 с».

Заміри на реальних даних показали, що віддавати всю історію погодинно не можна. Рядками-об'єктами
це 11.6 МБ, колонками 3.7 МБ, і в обох випадках 63 тис. точок у браузері. Подобово виходить 2 648
точок. Тому API дає вибір роздільності явно.

## What Changes

- `GET /prices?date_from=YYYY-MM-DD&date_to=YYYY-MM-DD&resolution=hour|day` під тим самим
  Basic Auth, що й решта API. Межі діапазону включні.
- **`resolution=hour`** (за замовчуванням) повертає сирі погодинні записи з усіма п'ятьма
  величинами. Діапазон обмежено **366 добами**, довший дає 422 з поясненням: для довгих
  діапазонів є `day`.
- **`resolution=day`** повертає по одному рядку на добу постачання без обмеження діапазону:
  - `price_min`, `price_max`;
  - `price_avg`, проста середня за періодами доби (відповідає індексу BASE);
  - `price_weighted`, середня, зважена за обсягом продажу. Саме цю цифру ОРЕЕ публікує як
    «середньозважену ціну»: для 26.09.2026 обидві дорівнюють 6560.60;
  - суми всіх чотирьох обсягів;
  - `periods`, кількість періодів у добі (23/24/25), щоб дні переходу часу було видно й тут.
- **Колонковий формат відповіді**: для кожного поля масив значень, а не масив об'єктів. Він утричі
  компактніший і лягає в ECharts без перетворень.
- Агрегація виконується в SQL (`GROUP BY` за добою постачання), а не в Python.
- Числа передаються як JSON-числа. Агреговані середні округлюються до 2 знаків, як і ціни в
  джерелі.
- Некоректні параметри повертають 422: відсутні дати, `date_from > date_to`, невідома
  роздільність, `hour` довше за 366 діб.

### Що НЕ входить у цю зміну

- Перетворення «дата + період» на мітку часу. За конвенцією проєкту це робить шар відображення,
  тобто зріз 10. API віддає `delivery_date` і `period` так, як вони є в джерелі.
- Інші роздільності (тиждень, місяць) і довільні агрегати.
- Сторінкування, експорт у CSV/Excel (Excel — non-goal брифу), кешування відповідей, gzip.
- Фільтр за зоною: зона в даних одна.
- UI, графік і таблиця — зрізи 10 і 11.
- Будь-які зміни схеми БД чи індексів. Заміри показують, що наявного первинного ключа вистачає.

## Capabilities

### New Capabilities

- `prices-api`: читання цін і обсягів РДН за діапазоном дат через HTTP з вибором роздільності.
  Погодинно з обмеженням діапазону або подобово з мін/макс/простою/зваженою середньою ціною
  і сумами обсягів, у колонковому форматі.

### Modified Capabilities

Немає. `http-api` уже вимагає Basic Auth на кожному ендпойнті, крім `/health`, і новий маршрут
підпадає під цю вимогу без її зміни. `dam-storage` не змінює поведінки: подобове читання
додається як нова операція репозиторію, а наявне читання за діапазоном лишається тим самим.

## Impact

- **Новий код:** маршрут `GET /prices` у `backend/app/api/`, подобове агрегатне читання в
  репозиторії.
- **Схема БД:** без змін.
- **Залежності:** нових немає.
- **Продуктивність:** за замірами, погодинний рік — 37 мс читання з БД і ≈ 0.5 МБ колонками;
  подобова вся історія — 2 648 рядків. Обидва варіанти вкладаються в бюджет «< 1 с» з запасом
  на рендер.
- **Розблоковує:** зріз 10 (`add-web-data-view`) отримує готовий контракт для графіка й таблиці.
- **Знімає борг** «Бюджет < 1 с для довгих діапазонів» із `docs/roadmap.md`.
