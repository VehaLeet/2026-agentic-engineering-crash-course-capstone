## Context

Мотивація й межі зміни описані в `proposal.md`, вимоги — у `specs/web-app/spec.md`.

Що вже є:

- `http-api`: `/health` без автентифікації; `/status`, `/runs/{id}`, `/collect` і `/prices` під
  Basic Auth. На 401 backend відповідає заголовком `WWW-Authenticate: Basic realm="oree-dam-monitor"`.
  `/docs` і `/openapi.json` вимкнено, тому генерувати типи з OpenAPI нема з чого.
- Контракт `/status`: `{last_run: Run | null, last_update: Run | null, recent_errors: Run[]}`,
  де в `Run` є `started_at` / `finished_at` в ISO 8601 UTC із суфіксом `Z`.
- Backend запускається як `uvicorn app.api.main:app --workers 1`, типово на порту 8000.
- Каталогу `frontend/` немає. На машині розробника Node 24, npm 11.

## Goals / Non-Goals

**Goals:**

- Нуль коду автентифікації у фронтенді й нуль змін у backend.
- Одна точка роботи з API (клієнт), щоб зрізи 10b і 11a додавали виклики, а не переробляли
  транспорт.
- Автентифікація, недоступність backend і зламаний контракт — три різні стани для користувача,
  а не одне «щось пішло не так».

**Non-Goals:**

- Продакшн-віддача збірки (див. борг контейнеризації в `docs/roadmap.md`).
- Кешування запитів і бібліотеки на кшталт React Query: поки що запит один, при завантаженні.
- Роутинг, дизайн-система, темна тема.

## Decisions

### Проксі Vite з префіксом `/api`, а не CORS

```
браузер -- http://localhost:5173 --+-- /            -> Vite (index.html, JS)
                                   +-- /api/*  --proxy--> http://localhost:8000/*
                                                          (префікс /api знімається)
```

Один origin дає дві речі одразу: не потрібна CORS-конфігурація на backend, і браузер надсилає
закешовані креди Basic Auth із кожним запитом до `/api`. Адреса backend береться зі змінної
`VITE_API_TARGET`, за замовчуванням `http://localhost:8000`. Вона читається лише конфігурацією
dev-сервера і в клієнтський бандл не потрапляє.

Префікс `/api` знімається, бо маршрути backend живуть у корені (`/status`, а не `/api/status`).
Змінювати backend заради фронтенду не потрібно.

Альтернатива — CORS на backend разом із `credentials: 'include'`. Її відкинуто: вона вимагає
змін у backend, і креди Basic Auth через CORS не кешуються браузером так само прозоро.

### Basic Auth через системне вікно браузера

Так вирішив користувач (див. proposal). Порядок такий: `fetch('/api/status')` отримує 401 з
`WWW-Authenticate: Basic`, браузер показує системне вікно, повторює запит із кредами і
запам'ятовує їх для цього origin до закриття браузера. Фронтенд бачить або 200, або, якщо
користувач натиснув «Скасувати», 401. Друге відображається станом «потрібна автентифікація».

`fetch` викликається з типовим `credentials: 'same-origin'`. Заголовок `Authorization` вручну
не додається: інакше браузер не керував би кредами сам.

**Ризик і запасний шлях.** Chrome і Firefox показують системне вікно й у відповідь на
`fetch`/XHR того самого origin. Але поведінка залежить від браузера, тож задача 4.1 перевіряє
її вручну в реальному браузері. Якщо вікно на `fetch` не з'явиться, стан «потрібна
автентифікація» містить посилання «Увійти» на `/api/status`. Перехід верхнього рівня гарантовано
викликає системне вікно, після чого креди вже закешовано для origin, і `fetch` проходить. Це
посилання корисне в будь-якому разі: воно дає шлях знову ввести креди після «Скасувати».

Виходу з системи немає, креди забуваються із закриттям браузера. Для 1–5 внутрішніх
користувачів це прийнятно, і так записано в non-goals.

### Клієнт API: один модуль, розрізнені помилки

```ts
class ApiUnauthorized extends Error   // 401
class ApiUnavailable  extends Error   // мережева помилка, 5xx, 502/504 від проксі
class ApiContractError extends Error  // 200, але тіло не відповідає контракту

getHealth():  Promise<{ status: 'ok' }>
getStatus():  Promise<SystemStatus>
```

`SystemStatus` і `Run` описано вручну за контрактом `http-api`, бо OpenAPI вимкнено. Щоб
розбіжність не лишилась непоміченою, відповідь `/status` проходить мінімальну перевірку форми:
перевіряється наявність ключів `last_run`, `last_update` і `recent_errors`, а також те, що
`recent_errors` — масив. Інакше клієнт кидає `ApiContractError`. Повна схема-валідація (zod
тощо) для трьох полів була б зайвою залежністю. Якщо зріз 10b покаже, що контрактів стало
більше, це рішення можна переглянути.

Недоступний backend під проксі Vite приходить як 502/504 або як мережева помилка, і обидва
випадки зводяться до `ApiUnavailable`.

### Сховище Zustand для стану з'єднання

```ts
type Connection =
  | { state: 'loading' }
  | { state: 'ok'; lastCheck: string | null; lastUpdate: string | null }
  | { state: 'unauthorized' }
  | { state: 'unavailable' }
  | { state: 'error'; message: string }

useConnection: { connection, check(): Promise<void> }
```

`check()` спершу викликає `/health`. Якщо він недоступний, повертається `unavailable`, і
захищений запит не робиться. Далі йде `/status`, а виняток клієнта зіставляється зі станом.
Так «backend лежить» і «не пройдено автентифікацію» ніколи не плутаються: `/health` не вимагає
кредів, і його відповідь однозначно показує, чи живий backend.

Сховище відокремлене від компонента, щоб зріз 11a міг викликати `check()` після «Оновити
зараз», а тести перевіряли зіставлення без рендерингу.

### Час за Europe/Kyiv

`Intl.DateTimeFormat('uk-UA', { timeZone: 'Europe/Kyiv', dateStyle: 'short', timeStyle: 'short' })`
в одній допоміжній функції `formatKyiv(iso)`. Часовий пояс браузера користувача при цьому не
враховується: сервіс про український ринок, і опорну дату збору теж узято за Києвом. Тест
фіксує, що `2026-09-28T09:00:00Z` відображається як `28.09.26, 12:00` (з урахуванням літнього
часу, EEST = UTC+3).

### Структура

```
frontend/
  package.json, package-lock.json, tsconfig*.json, eslint.config.js
  vite.config.ts        -- проксі /api, налаштування Vitest (jsdom)
  index.html
  README.md             -- як запустити backend + frontend
  src/
    main.tsx
    App.tsx             -- заголовок + ConnectionPanel
    api/client.ts       -- getHealth, getStatus, класи помилок
    api/types.ts        -- Run, SystemStatus
    state/connection.ts -- Zustand-сховище
    lib/time.ts         -- formatKyiv
    components/ConnectionPanel.tsx
    **/*.test.ts(x)
```

Проєкт генерується `npm create vite@latest frontend -- --template react-ts`. Все зайве з
шаблону (логотипи, лічильник, демо-CSS) видаляється, щоб у репозиторії не лишалося мертвого коду.

### Тести

Vitest + Testing Library + jsdom. `fetch` підміняється на рівні `globalThis` у тестах клієнта,
а сховище підміняється в тестах компонента. Мережі й запущеного backend тести не потребують.
Проксі й системне вікно браузера перевіряються вручну (задачі групи 4), бо jsdom їх не має.

Схема БД і контракти API не змінюються.

## Risks / Trade-offs

- **Браузер не покаже системне вікно на `fetch`** → запасне посилання «Увійти» на
  `/api/status` (див. вище). Поведінку перевіряє ручна задача 4.1.
- **Немає кнопки «Вийти»** → креди живуть до закриття браузера. Прийнятно для внутрішнього
  сервісу на 1–5 користувачів. Власна форма входу — окреме рішення, воно потребує змін у backend.
- **Ручні типи можуть розійтися з backend** → мінімальна перевірка форми дає `ApiContractError`
  замість тихих `undefined`. Ризик зростатиме з кожним новим ендпойнтом, тож у зрізі 10b варто
  переоцінити.
- **Порожні `last_run`/`last_update` — нормальний стан свіжої БД** → показуються як «ще не
  було», а не як помилка.
- **Продакшн-збирання існує, але його нікому віддавати** → `npm run build` перевіряється як
  критерій якості, а віддача збірки йде з боргом контейнеризації.

## Migration Plan

Міграцій немає. Розгортання для розробки: `npm ci` у `frontend/`, далі `npm run dev` поряд із
