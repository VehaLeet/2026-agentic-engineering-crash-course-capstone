# OREE DAM Monitor — Product Brief

## Проблема
Результати торгів на ринку «на добу наперед» (РДН) від ОРЕЕ доводиться перевіряти вручну.
Потрібен сервіс, який сам відстежує появу нових даних, зберігає їх і сповіщає в Telegram.

## Для кого
Одна людина або невелика команда (1–5 користувачів). Сервіс внутрішній, не публічний.

## MVP-функції
1. **Збір даних.** Періодично (за замовчуванням раз на годину) завантажувати офіційний CSV з OREE (DAM),
   парсити його і зберігати в Postgres: ціни та обсяги торгів по періодах доби.
2. **Детекція оновлень.** Визначати, чи дані змінились з минулого запуску
   (хеш вмісту CSV, а не лише дата). Зберігати час останнього успішного оновлення.
3. **Сповіщення в Telegram.** Якщо з'явились нові/змінені дані, надсилати повідомлення
   в налаштовані чати (користувачі та/або канал). Короткий зміст: дата поставки, мін/макс/середня ціна.
4. **Журнал запусків.** Кожен запуск записується: час, статус (success / no_changes / error), помилка.
5. **Веб-інтерфейс:**
   - перегляд даних: графік (ECharts) + таблиця;
   - фільтр історичних даних за діапазоном дат (і зоною, якщо їх кілька);
   - кнопка «Оновити зараз» (ручний запуск того самого збору);
   - налаштування: отримувачі Telegram (chat_id), частота моніторингу, увімк/вимк сповіщення;
   - статус: остання перевірка, останнє оновлення даних, останні помилки.

## Non-goals (свідомо НЕ робимо в MVP)
- Мультитенантність, ролі, реєстрація користувачів.
- Інші джерела даних окрім OREE DAM (але парсер ізолювати за інтерфейсом).
- Інтерактивний Telegram-бот (команди, діалоги) — тільки відправка повідомлень.
- Прогнозування цін, аналітика, експорт у Excel.
- Горизонтальне масштабування.

## Технічний стек
- **Backend:** Python 3.12+, FastAPI, SQLAlchemy 2.x (async), Alembic, Postgres 16, APScheduler.
- **Telegram:** прямі виклики Bot API (`sendMessage`) через httpx — без фреймворку ботів.
- **Frontend:** React + TypeScript, Vite, ECharts, Zustand.
- **Інфраструктура:** docker-compose (postgres, backend, frontend), монорепо `backend/` + `frontend/`.

## Ключові технічні рішення та обмеження
- **Одне джерело правди для налаштувань — БД.** Зміна частоти з UI перепланує job APScheduler без рестарту.
- **Секрети лише в env:** `TELEGRAM_BOT_TOKEN`, `DATABASE_URL`, креди для доступу до UI. Токен не показується і не редагується в UI.
- **Захист від паралельних запусків:** плановий і ручний запуск не повинні виконуватись одночасно
  (Postgres advisory lock). Backend запускається з одним воркером, або scheduler винесено в окремий процес.
- **Ідемпотентність:** повторний збір тих самих даних не створює дублікатів (upsert за
  унікальним ключем: дата поставки + період + зона).
- **Часова зона:** Europe/Kyiv; коректна обробка днів переходу на літній/зимовий час (23/25 годин).
- **Доступ до UI:** щонайменше Basic Auth або один адмін-логін через env.
- **Надійність:** таймаути та ретраї на завантаження CSV і відправку в Telegram;
  помилка відправки в одного отримувача не зриває решту.

## Відкриті питання (з'ясувати на етапі explore)
- Точний URL і формат CSV OREE DAM: колонки, кодування, роздільник, формат дат/чисел.
- Гранулярність даних: погодинна чи 15-хвилинна.
- Які торгові зони є в даних і чи потрібні всі.
- Коли OREE зазвичай публікує результати (для розумного розкладу перевірок).
- Чи треба зберігати сирі CSV-файли для аудиту.

## Критерії успіху MVP
- Нові дані з'являються в БД не пізніше ніж через один інтервал моніторингу після публікації.
- Сповіщення приходить рівно один раз на кожне реальне оновлення.
- Історію за будь-який діапазон дат видно на графіку за < 1 с.
