# OREE DAM Monitor — Product Brief

## Проблема
Результати торгів на ринку «на добу наперед» (РДН) від ОРЕЕ доводиться перевіряти вручну.
Потрібен сервіс, який сам відстежує появу нових даних, зберігає їх і сповіщає в Telegram.

## Для кого
Одна людина або невелика команда (1–5 користувачів). Сервіс внутрішній, не публічний.

## MVP-функції
1. **Збір даних.** Періодично (за замовчуванням раз на годину) завантажувати офіційний
   квартальний CSV з OREE (DAM), парсити його і зберігати в Postgres: ціни та обсяги торгів
   по періодах доби (всі 5 числових колонок джерела).
2. **Детекція оновлень.** Визначати, чи дані змінились з минулого запуску, за хешем вмісту,
   а не за датою. Два рівні: хеш завантаженого файлу (дешевий ранній вихід «без змін») і хеш
   кожної доби постачання (дає перелік конкретно змінених діб для тексту сповіщення і ловить
   ретроспективні перерахунки OREE). Зберігати час останнього успішного оновлення.
3. **Сповіщення в Telegram.** Якщо з'явились нові/змінені дані, надсилати повідомлення
   в налаштовані чати (користувачі та/або канал). Короткий зміст: дата поставки, мін/макс/середня ціна.
4. **Журнал запусків.** Кожен запуск записується: час, статус
   (success / no_changes / no_data / error / skipped_locked), помилка. `skipped_locked` —
   запуск, що не отримав блокування записувачів (вже йде інший збір або бекфіл): не помилка
   і не «без змін».
5. **Веб-інтерфейс:**
   - перегляд даних: графік (ECharts) + таблиця;
   - фільтр історичних даних за діапазоном дат;
   - кнопка «Оновити зараз» (ручний запуск того самого збору);
   - налаштування: отримувачі Telegram (chat_id), частота моніторингу, увімк/вимк сповіщення;
   - статус: остання перевірка, останнє оновлення даних, останні помилки.

## Non-goals (свідомо НЕ робимо в MVP)
- Мультитенантність, ролі, реєстрація користувачів.
- Інші джерела даних окрім OREE DAM (але парсер ізолювати за інтерфейсом).
- Інтерактивний Telegram-бот (команди, діалоги) — тільки відправка повідомлень.
- Прогнозування цін, аналітика, експорт у Excel.
- Горизонтальне масштабування.

## Технічний стек
- **Backend:** Python 3.12+, FastAPI, SQLAlchemy 2.x (async), Alembic, Postgres 16, APScheduler.
- **Telegram:** прямі виклики Bot API (`sendMessage`) через httpx — без фреймворку ботів.
- **Frontend:** React + TypeScript, Vite, ECharts, Zustand.
- **Інфраструктура:** docker-compose (postgres, backend, frontend), монорепо `backend/` + `frontend/`.

## Ключові технічні рішення та обмеження
- **Одне джерело правди для налаштувань — БД.** Зміна частоти з UI перепланує job APScheduler без рестарту.
- **Секрети лише в env:** `TELEGRAM_BOT_TOKEN`, `DATABASE_URL`. Токен не показується і не редагується в UI.
- **Захист від паралельних запусків:** плановий і ручний запуск не повинні виконуватись одночасно
  (Postgres advisory lock). Backend запускається з одним воркером, або scheduler винесено в окремий процес.
- **Ідемпотентність:** повторний збір тих самих даних не створює дублікатів (upsert за
  унікальним ключем: дата поставки + період). Зона в ключ не входить — у даних вона одна.
- **Часова зона:** Europe/Kyiv. Дні переходу на літній/зимовий час (23/25 годин) не потребують
  окремої логіки: кількість періодів визначається вмістом CSV. Конвертація періоду в мітку
  часу — задача шару відображення, не збору.
- **Доступ: MVP без автентифікації, лише localhost.** На ранньому етапі мета — показати
  функціональність, тому API і UI не мають входу. Межею доступу є мережевий інтерфейс: API
  слухає лише loopback (запуск з іншою адресою відмовляє), Postgres прив'язаний до
  `127.0.0.1`. Сервіс доступний лише розробнику на його машині.
- **Session-based автентифікація і TLS — окремий етап.** Перш ніж сервіс стане доступним
  будь-кому, крім розробника, потрібні моделі `user` і `session` на backend, власна сторінка
  входу і HTTPS. Проміжних рішень (Basic Auth, пароль у сховищі браузера) свідомо не робимо.
- **Надійність:** таймаути та ретраї на завантаження CSV і відправку в Telegram;
  помилка відправки в одного отримувача не зриває решту.

## Джерело даних (з'ясовано на етапі explore)

```
GET https://www.oree.com.ua/index.php/control/results_mo_stat_csv/DAM/{year}/{quarter}
    -> 200, text/csv; charset=utf-8
       Content-Disposition: attachment; filename="results_mo_DAM_2026_Q3.csv"
```

Ендпойнт офіційно лінкується зі сторінки `/index.php/control/results_mo_stat/DAM`, тобто це
підтримуваний публічний експорт. Автентифікація не потрібна.

- **Формат:** UTF-8 **з BOM** (читати як `utf-8-sig`), переноси **CRLF**, роздільник **`;`**,
  без лапок. Дати `DD.MM.YYYY`, числа з десятковою точкою (ціна — 2 знаки, обсяги — 1).
- **Колонки (7):** `Дата;Година;Ціна, грн/МВт.год;Обсяг продажу, МВт.год;Обсяг купівлі, МВт.год;`
  `Заявлений обсяг продажу, МВт.год;Заявлений обсяг купівлі, МВт.год`. Назви колонок містять
  коми — саме тому роздільник `;`.
- **Гранулярність:** погодинна. `Година` — це порядковий номер періоду 1..25, а **не** година
  доби; зберігати як є, без конвертації.
- **Дні переходу часу** зашиті в самі дані: 30.03.2025 має 23 рядки, 26.10.2025 — 25.
  Власної логіки DST не потрібно.
- **Торгові зони:** одна. Колонки зони в CSV немає, тому зона не є виміром даних і фільтр
  за зоною в UI не потрібен.
- **Публікація:** результати на добу постачання D з'являються в день D-1, приблизно
  12:30–13:00 за київським часом (аукціон закривається близько 12:00).
- **Одиниця завантаження — квартал, а не доба.** Наслідок: збір за опорну дату мусить тягнути
  квартал цієї дати **і** квартал наступної доби, бо на межі кварталу (напр. 30.09) завтрашня
  доба постачання вже належить наступному файлу.
- **Порожній квартал — не помилка.** Квартал до запуску ринку, майбутній квартал і навіть
  номер кварталу 5 повертають HTTP 200 із самим лише рядком заголовків. Код відповіді не
  розрізняє наявність даних — єдиний критерій це кількість розібраних рядків.
- **Обсяг:** ~2200 рядків і ~110 КБ на квартал. Історія починається з **01.07.2019**
  (запуск РДН): ~29 файлів, ~63 тис. рядків — повний бекфіл дешевий.
- **Сирі CSV зберігаємо** для аудиту, але **лише коли хеш змінився** (інакше щогодинні 110 КБ
  дали б ~1 ГБ/рік ідентичних копій; при збереженні на зміну це ≈ 40 МБ/рік).
- **Запасний шлях,** якщо експорт зникне: недокументований AJAX-ендпойнт сторінки результатів
  `POST /index.php/PXS/get_pxs_hdata/{DD.MM.YYYY}/DAM/2` віддає JSON із погодинними даними.
- **Ринок ВДР** (`.../results_mo_stat_csv/IDM/...`) має інший набір колонок (10 замість 7) —
  ще одна причина ізолювати джерело за інтерфейсом. Поза межами MVP.

## Відкриті питання
- Конкретні значення таймауту і кількості ретраїв на завантаження (безпечні дефолти
  спочатку, уточнити після спостереження за реальною поведінкою OREE).
- Чи варто згодом замінити погодинний розклад на частіші перевірки у вікні 12:00–15:00
  Europe/Kyiv. Не в MVP.

## Критерії успіху MVP
- Нові дані з'являються в БД не пізніше ніж через один інтервал моніторингу після публікації.
- Сповіщення приходить рівно один раз на кожне реальне оновлення.
- Історію за будь-який діапазон дат видно на графіку за < 1 с.
